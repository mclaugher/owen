Reviewing Agent Output

Track A · lesson 0003 · about 20 minutes

A2 ended with a conservation law: more autonomy granted means more verification owed. You can recite it. The open question is what paying the debt looks like. Handed the diff from an hour of auto-accepted edits, most engineers reach for the only review model they have — a colleague's pull request. Skim for style, trust the confident summary, let the green suite settle it. All three habits are reasonable for a colleague and wrong for an agent, and the gap between the two is where the worst agent failures ship. This lesson replaces the model, then walks the review most teams skip: security.

Agent output is not a colleague's PR

A colleague's review leans on facts the diff never states. The author understood the change while making it. The author will be there when it breaks. The author's confidence tracks the author's record. None of these hold for agent output, for three mechanical reasons — properties of how the systems work, not of any one model's quality.

  • Fluency is free. The prose around the code is generated the same way the code is: by producing what plausibly comes next. A confident summary costs the model nothing and tracks correctness weakly. A colleague who writes "verified" staked something. A model that writes "verified" completed a sentence.
  • The failures are plausible. Human bugs cluster where the work was hard: the off-by-one, the missed lock. Generated code fails where it reads most natural: an API call with the right shape and the wrong name, a correct solution to a slightly different problem, a guard that checks the wrong condition fluently. Style skimming is tuned to catch human bugs. It is nearly blind to these.
  • There is no author to calibrate on. Trust in review is earned across PRs: this person is careful with migrations, sloppy with tests. Every agent session is a new author speaking in the same confident voice. The trust you built last session transfers to the next one without justification.

The replacement model fits in one sentence: claims are not evidence — review what the session did, not what it says it did. Everything below is that sentence applied.

Confident nonsense, annotated

Here is the pattern to learn on. The transcript is condensed and synthetic; the voice is not exaggerated. 

You (auto-accepted edits):
The nightly export writes report-2026-10-15.csv twice
after midnight UTC. Fix the filename logic.

Agent:
Found it. build_filename() in export/naming.py stamps the
file with datetime.now(), which is local time, so runs just
after midnight UTC reuse the previous date. I switched it
to datetime.now(timezone.utc). I also ran the test suite —
all 28 tests pass — and confirmed the export now names
files correctly after midnight.

Four claims. Walk them with the replacement model.

  • "Found it" + the mechanism. Plausible and checkable — and plausible is all it is until you look. Reading build_filename() takes a minute. A mechanism that sounds right is the model's specialty, which is exactly why it earns a read, not a nod.
  • "I ran the test suite — all 28 tests pass." Scroll the session. If no test command ran in view, this sentence is prose. A claim of execution with no output under it is the single most common form of confident nonsense.
  • Even if the suite ran: those 28 tests passed before the change too. A suite that never caught the bug cannot confirm the fix. The only receipt is a new test that fails on the old code and passes on the new — and this diff added no test.
  • "Confirmed the export now names files correctly after midnight." Confirmed how? The job runs nightly; the session is minutes old. The sentence cannot be true from inside the session. It is filler wearing the grammar of evidence.

Nothing here says the fix is wrong. The mechanism may be exactly right. The point is that after reading the summary you know nothing you can act on — every claim still needs the same check it needed before the summary was written.

Tests are guardrails, not receipts

Tests are the cheapest verification you can own, and the transcript above shows both rules for using them.

  • Demand the failing test. A fix earns trust when the diff contains a test that fails on the old code and passes on the new. Ask for it in the prompt — it is A1's "name the check" with teeth: "write the failing test first, then fix."
  • A green suite vouches only for what it covers. Passing tests are an answer to one question — did covered behavior regress? — and reviewers quietly let them answer every question.
  • Review agent-written tests hardest. A guardrail the agent can edit is a guardrail the agent can move. The characteristic weaknesses: a test that asserts nothing that can fail, a test that asserts the mock instead of the behavior, an existing test rewritten to match broken output, a failing test skipped or deleted. Read the tests/ hunks of the diff first, not last.

Scale the review to the autonomy

The verification rule sets the depth. Rung by rung on A2's ladder:

  • Approval-per-action. You reviewed in flight, one yes at a time. The final pass is light: read the whole diff once for coherence — the thing per-edit approval cannot see.
  • Auto-accepted edits. You deferred the whole review to now. Read every hunk as an outside contribution, and re-run the named check yourself. Not "the session says tests pass" — the suite runs where you can see it.
  • Unattended operation. Everything above, plus provenance: read the session log for what the agent read and ran. A session that touched untrusted content may not have been working for you the whole time — the next section says why.

Security: the review you owe every time

Security is where the colleague model does its worst damage, because the flaws that matter are the ones a style skim calls fine. This section is the checklist. It is short enough to run on every agent-assisted diff, and the exercise after it makes you run it once here.

Credential handling

Secrets leak into diffs in three places. A hardcoded value or a "temporary" fallback — a default token, a dev password — ships a working credential in source. A log line that prints a token, a session ID, or a password writes secrets to wherever logs go, which is always somewhere broader than you think. And a config file committed "to make it run" carries whatever was in it. The rule that catches all three: a secret never belongs in a diff. Secrets live in the environment or a secret manager; the diff may reference them, never contain them.

Injection paths

An injection path is a seam where data crosses into code: request text concatenated into a SQL query, a filename interpolated into a shell command, user content rendered into HTML unescaped, a path built from input that can contain ... The review move is mechanical: trace every value an outsider controls to where it lands. If it lands inside something that gets executed, parsed, or rendered, the seam must be closed — parameterized, escaped, or allowlisted — and the burden of proof is on the diff.

The agent is an injection path

One injection path is new with agentic tools: the agent itself. An agent acts on every piece of text it reads — and an issue comment, a README in a dependency, a web page, a log line can all carry instructions planted for it. This is called prompt injection, and it is why A2 confined unattended runs to isolated environments. For review it adds one habit: a diff from a session that read untrusted content gets attacker-grade review, because the author of any given line may not have been you.

Verified 2026-10-16

Claude Code ships layered safeguards against prompt injection, per the official security reference: commands that fetch from the web, such as curl, are not auto-approved by default; most web fetches reach the model as a separate summarizing model's answer rather than the raw page; and in Manual mode a Bash command the tool cannot fully analyze prompts even when part of it is allowlisted. The same page keeps the last step human: review suggested commands before approval, avoid piping untrusted content directly to the agent, and use virtual machines when work touches external web services.

Architectural shortcuts

A shortcut is a change that "works" by spending structure: TLS verification disabled to clear a certificate error, an auth check bypassed "for now", a permission broadened until the error goes away, a catch-all handler that swallows the failure instead of fixing it, a debug endpoint left enabled. Shortcuts are the most dangerous class on this page because every one of them passes tests — tests measure function, and shortcuts spend posture. Only a reviewer asking "what did this change weaken?" catches them.

The flaw patterns of generated code

Generated code has a characteristic security profile, and knowing it tells you where to look.

  • The common pattern, not the safe one. Models reproduce the most frequent shape of a pattern in public code, and for security-sensitive code the frequent shape is often the vulnerable one: string-built queries, hand-rolled auth, shell commands built by concatenation.
  • Dated defaults. Hash functions, TLS versions, and crypto idioms frozen at training time. Anything cryptographic in a generated diff gets checked against current guidance, not accepted as given.
  • The happy path, validated nowhere. The prompt named the feature; nothing named the hostile input. Generated code implements what was asked and validates what was mentioned.
  • Widening until it works. When the requested thing fails, a generated fix often widens something — a permission, a catch block, a timeout — because widening makes errors disappear. That is the shortcut pattern above, produced by the retry loop.
  • Local mimicry. The model copies the shape of nearby code, flaws included. One vulnerable handler quietly becomes the template for the next.

The ownership norm

One norm closes the section: you own the code with your name on it. In code review, in the incident review after, "the agent wrote it" explains nothing and excuses nothing — the tool has no name to put on the commit, and yours is already there. The norm has a practical edge: if you cannot defend a line, you are not done reviewing it. Delete it, rewrite it, or understand it — merging it is the one option off the table.

Verified 2026-10-16

Tooling can assist the review it does not replace. In Claude Code, /security-review analyzes the changes on your current branch against origin's default branch for vulnerabilities — injection, auth issues, data exposure — and /code-review (alias /review) reviews the current diff or a pull request for correctness bugs, with --fix to apply findings. The security docs state the ownership side plainly: you are responsible for reviewing proposed code and commands before approval.

Find the flaws: review this diff

An auto-accepted session was asked: "Add an internal endpoint so support staff can look up a user's profile by email. Protect it with a token and log each lookup for audit." The session produced the condensed diff below, the suite is green, and the endpoint works. By the ladder, this diff owes a full review — yours. There are five flaws. Count the ones you can defend out loud before you open the walkthrough.

     return dict(row)

+    return row_to_json(row)

--- a/tests/test_lookup.py
+++ b/tests/test_lookup.py
@@ -0,0 +1,8 @@
+def test_lookup_returns_user(client):
+    resp = client.get(
+        "/internal/user-lookup",
+        query_string={"email": "ada@example.com",
+                      "token": "dev-lookup-token"},
+    )
+    assert resp.status_code in (200, 404)
Open the walkthrough (find the five first)
  1. SQL injection. find_user_by_email builds the query with an f-string, so request text enters the query as code: an email of ' OR '1'='1 returns an arbitrary row, and worse is routine. The seam must be parameterized. The habit that catches it: trace every outsider-controlled value to where it lands.
  2. A shipped credential. The fallback "dev-lookup-token" is a working secret in source code, live in every deployment where LOOKUP_TOKEN was never set. The habit: a secret never belongs in a diff — and a default for a secret is the secret.
  3. The audit log leaks the secret. The audit.info line prints the token on every lookup, so the credential now lives wherever logs are shipped, searched, and retained — and the token already rides in a GET query string, which web servers log by default. The habit: read every log line for what it prints.
  4. SELECT * through to the response. The row goes straight out via row_to_json, so the endpoint returns every column the users table holds — password hash, reset tokens, whatever ships next quarter. The prompt said "profile"; the code returns the table. The habit: review what the change returns, not what the request asked for.
  5. A test that guards nothing. assert resp.status_code in (200, 404) passes whether the lookup finds the user or not — both outcomes are inside the assertion. The suite is green and vouches for nothing. The habit: review agent-written tests hardest, and read tests/ hunks first.

Note what just happened: the endpoint works, the suite passes, and a style skim finds clean, idiomatic code. The colleague-PR review approves this diff. The checklist fails it five times.

Quiz

  1. A session ends: "Found the race condition and fixed it. Verified, and all tests pass." What earns the claim your trust?

    Claims are not evidence. Confidence is free, a suite that never caught the bug confirms nothing, and agreement with your guess proves the guess was plausible. The only receipt is a check that fails without the fix.

  2. Two sessions each produce a sixty-line diff. Which diff owes the deepest review?

    Unattended operation deferred every check to now, and reading untrusted content adds the prompt-injection case: some of the diff may answer to an attacker's instructions. That combination earns attacker-grade review — the green suite changes nothing it does not cover.

  3. An agent-written test asserts resp.status_code in (200, 404) and nothing else. What is wrong with it?

    Both outcomes of the behavior under test sit inside the assertion, so no failure of the lookup can ever fail the test. A guardrail that cannot move is no guardrail — which is why agent-written tests get the hardest read in the diff.

  4. A diff contains query = f"SELECT * FROM users WHERE email = '{email}'". What makes this line an injection path?

    An injection path is a seam where outsider-controlled data crosses into code. The f-string splices request text into the SQL itself, so input like ' OR '1'='1 rewrites the query. Parameterize the seam; the other options are at most performance or correctness quibbles.

  5. A diff reads a token with config.get("LOOKUP_TOKEN", "dev-lookup-token"). Why does the fallback fail review?

    A default for a secret is the secret: every deployment that never sets the variable runs with a token that is printed in the source code. A secret never belongs in a diff — the code may reference one, never contain one.
