The Mental Model

Track A · lesson 0001 · about 15 minutes

The primer taught one mechanism. One context window holds everything the agent sees: your messages, every file read, every command output. Tokens accumulate, and accuracy degrades as they do. This lesson turns that mechanism into the highest-leverage habit in agentic coding, names the two dials you will meet on day one, and hands you four safe first tasks.

Doesn't a huge window solve this?

The primer's dated callout listed window sizes, and they are large. A fair objection follows: with that much room, why keep tasks small at all? The objection deserves a direct answer, because the window sizes keep growing and the answer does not change.

Verified 2026-10-15

Every model in the current Claude lineup — frontier tier through small tier — now has a 1-million-token context window. The objection above is at its strongest today. The three reasons below still hold.

A bigger window is not a sharper window, for three reasons:

  • Degradation does not wait for the window to fill. Recall declines as tokens accumulate — the gradient the primer called context rot. The model's attention budget draws down with every token added, from the first one. A larger window raises the ceiling. It does not move the gradient.
  • What fills the window matters as much as how full it is. A failed attempt does not sit in the window neutrally. It misleads. A big window holds more stale reads, more dead ends, more contradicting attempts — and the model weighs all of them.
  • You pay for every token either way. Tokens are billed whether the model used them well or not. A sprawling session costs more and produces less.

So the window model survives its own good news. However large the buffer, the task that stays small works in the sharp part of the gradient, carries no debris, and costs less. Window size changes none of that.

The habit: small, focused tasks

The primer's pointer asked you to list the files an agent would need for one task. That list is the task's context footprint: the files read, the outputs generated, the conversation spent. The single highest-leverage habit in agentic coding is to keep that footprint small — one goal, nameable files, one check that proves the work. The official best-practices guide states the same derivation: most best practices follow from one constraint — the window fills fast, and performance degrades as it fills.

Three things follow from the window model, not from taste:

  • A small task keeps the whole session in the sharp range of the gradient. The model recalls your constraints because few tokens separate it from them.
  • A small task is cheap to verify. One goal and one check mean you can read the diff and run the check in minutes.
  • A small task is cheap to retry. When an attempt goes wrong, you restart in a fresh window and lose little. A sprawling task that goes wrong leaves you correcting code inside a polluted window — the expensive path from the primer's worked example.

"Small" is a statement about scope, not about importance. "Why does login fail after a session timeout?" is small. "Improve our auth" is not — however few characters it takes to type.

The two dials

Every agentic coding tool exposes two controls that shape cost and capability. This lesson only names them. Track B teaches when to turn them.

  • Dial one: which model tier. Frontier models reason deepest and cost the most. Mid-tier models trade some capability for speed and price. Small-tier models run fast and cheap for high-volume, simple work.
  • Dial two: how hard the model thinks. The same model can spend more tokens reasoning before it answers, or fewer. More thinking buys depth on hard problems and costs tokens and time on easy ones.

For your first sessions, the defaults are fine. What matters now is knowing the dials exist: when a task underperforms or overspends, these are the first two settings to question.

Verified 2026-10-15

The current Claude lineup maps to the tiers like this: Claude Opus 5.5 is the frontier-tier default, with Claude Fable 5.1 above it for the most demanding reasoning; Claude Sonnet 5.5 is the mid tier; Claude Haiku 5.5 is the small tier. The thinking dial is the effort setting, with five levels from low to max. Names and levels change between releases. The two dials do not.

Four first wins

These four tasks are the standard menu for a first week. They are not four tricks. Each is an instance of one property: bounded scope, checkable outcome, small context footprint.

  • Stack-trace analysis. The trace bounds the scope: it names the files and the failing line. The outcome is checkable: the error reproduces or it does not. The footprint is the trace plus a few files.
  • A named refactoring. "Extract the retry logic in client.py into one function" bounds scope to named code. The existing tests are the check. The footprint is one or two files.
  • Test generation. "Write tests for parse_duration, covering negative input" bounds scope to one behavior. The outcome checks itself: the tests run. The footprint is the function and its callers.
  • Codebase questions. Ask what you would ask a senior engineer: "How does logging work here?" The scope is one question. The check is reading the cited code yourself. The footprint is the agent's reads — and a wrong answer costs you nothing to discard.

The menu is not the lesson; the property is. Any task with all three clauses is a first win, including tasks this menu never names. And a menu item phrased without bounds loses the property: "refactor the service" is not a named refactoring, and "add tests for the payment module" is not test generation. The property, not the category, does the work.

Worked example: one stack trace, start to finish

A nightly report job fails. The log ends with this trace. Read it yourself first: where would you look, and what would you want to know? 

Traceback (most recent call last):
  File "app/jobs/report.py", line 48, in build_summary
    totals = aggregate(rows)
  File "app/jobs/aggregate.py", line 21, in aggregate
    bucket[row["region"]] += row["amount"]
KeyError: 'region'

Now the prompt. Note how little it takes to satisfy the property: the trace bounds the scope, a named directory narrows the search, and the last line requests a checkable deliverable. 

The nightly report job failed with the trace below. The rows
come from the CSV importer in app/jobs/ingest.py. Why is
"region" missing, and what is the smallest fix? Name the
commit-sized change and the test that would have caught this.

[trace pasted here]

A plausible reply, condensed:

Read app/jobs/aggregate.py and app/jobs/ingest.py.

Cause: ingest.py line 33 now emits the column as
"sales_region" (renamed in the importer two weeks ago);
aggregate.py line 21 still reads row["region"]. Every
row raises KeyError on the first lookup.

Smallest fix: read "sales_region" in aggregate.py, or
restore the name at the importer boundary. The boundary
fix is safer: three other consumers also read "region".

Missing test: a round-trip test that feeds one imported
row into aggregate() — it fails on the rename.

Walk the property through what happened:

  • Bounded scope. The agent read two files, because the trace and the prompt named them. No exploration spiral.
  • Small footprint. A trace runs a few hundred tokens; two files a few thousand. The whole exchange fits in the sharpest part of the window.
  • Checkable outcome. The claimed cause names two lines you can open and read. The proposed test fails before the fix and passes after. You verify in minutes — and the answer about three other consumers is exactly the kind of claim you check rather than trust.

This is the shape to copy: evidence in, named files, a deliverable the code itself can confirm.

Quiz

  1. Which request is the best first task for an agent?

    One behavior, a few files, and an answer the code can confirm: bounded scope, checkable outcome, small footprint. The other three are unbounded, uncheckable, or both.

  2. What single property do all four first wins share?

    The menu is four instances of one property. Any task with all three clauses qualifies, whether or not the menu names it.

  3. Why does a small task produce sharper output than a sprawling one?

    Accuracy degrades as tokens accumulate. A small footprint keeps the whole session early on that gradient, where recall is strongest.

  4. What are the two dials this lesson names?

    Model tier and thinking depth. Both trade capability against cost. Track B teaches when to turn them; for now, know they exist.

  5. You ask for "tests for the payment module." The agent reads forty files and writes shallow tests. Which clause did the request break?

    A module is a territory; a behavior is a task. Name the function and the edge case, and the footprint shrinks to match. The dials were never the problem.

Optional: pick one bug or one question from your current work and write the prompt you would hand an agent — the goal, the files involved, and the check that proves the work. Keep it. It is your first session's opening move.
