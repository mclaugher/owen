Scoping and Modes

Track A · lesson 0002 · about 15 minutes

A1 ended with a prompt in three parts: the goal, the files, the check. It left one question open: when is a task small enough to skip the planning pass? The question matters because engineers miss it in both directions. Some treat planning as a ritual and plan every one-line fix. Others skip planning on multi-file work because the request was short to type — and A1 already showed why short to type is not small in scope. This lesson gives you the test that settles it, the four modes every agentic tool offers, and one rule you will carry into the next lesson.

Spend tokens on purpose

The primer showed where tokens go by default: wherever the session drifts. This lesson is about spending them on purpose, and the flagship discipline is plan before code. A planning pass is a session, or a mode, in which the agent can read but not change. It reads the files, maps the blast radius, and hands you a plan. You spend reading-and-deciding tokens before any editing tokens — the same investment the primer's worked example priced: a bounded cost up front against an unbounded debugging spiral later.

A plan has one property no diff has: it is the cheapest artifact you will ever correct. Cutting a step from a plan costs one sentence. Cutting the same step out of finished code costs a review argument and a rewrite — inside a window already polluted by the attempt.

The test: name the files and the check

So when do you skip the pass? Use one test. Skip the planning pass when you can name every file the change touches and the check that proves the work. Plan when you cannot.

The test works because it measures the right thing. When you can name the files and the check, the plan already exists — in your head. Asking the agent to write it again is the ritual. When you cannot name them, someone has to find them, and the planning pass finds them at the price of reads instead of the price of wrong edits. Notice what the test ignores: how long the request took to type, and how urgent the work feels. "Fix the typo on line 80 of README.md" names the file and the check — skip. "Rename the config key timeout everywhere it is used" is nine words, and you cannot name its files — plan.

The four modes

Agentic tools expose a ladder of operating modes. The names vary by tool and by release; the rungs do not.

  • Read-only planning. The agent reads and proposes. Nothing on disk changes until you approve.
  • Approval-per-action. The agent works, and each consequential action — an edit, a command — waits for your yes.
  • Auto-accepted edits. Edits apply without asking. You review the result, not each step.
  • Unattended operation. The agent runs with no one watching. The environment it runs in is the only boundary left.

Each rung down the list trades control for flow. The trade is real: approval prompts interrupt, and an hour of them makes the next rung look attractive. That is exactly the failure to avoid. Match the mode to the risk of the work, not to your patience. Risk is a property of the task: what the change can break, and how cheaply you can undo it. A scratch-branch prototype under fast tests earns auto-accepted edits — the blast radius is a branch you can delete. An edit near deploy configuration earns approval-per-action however tedious the prompts feel, because your patience ran out and the blast radius did not shrink.

Verified 2026-10-15

In Claude Code the ladder maps to named permission modes: Manual mode (config value default) asks before most actions; acceptEdits applies file edits without asking; plan blocks edits until you approve a plan; bypassPermissions runs everything without prompts. Two modes sit beside the ladder: auto, the current starting mode for interactive sessions, where a second model reviews actions instead of you; and dontAsk, for locked-down scripts, which denies anything that would prompt. Press Shift+Tab mid-session to cycle modes — the status bar shows the active one, such as ⏸ plan mode on. Start a session in a mode with claude --permission-mode <mode>, or send a single planned prompt by prefixing it with /plan. Mode names and keybindings change between releases. The rungs do not.

The verification rule

One rule governs the whole ladder, and the next lesson is built on it: more autonomy granted means more verification owed.

Verification does not disappear when the prompts do. It moves. Approval-per-action spreads verification through the session, one small yes at a time. Auto-accepted edits defer it to one sitting: the full diff, reviewed at the end. Unattended operation defers everything — you owe the session's entire output a review it never got while running. Read the rule as a conservation law: every prompt you turn off becomes review you owe later. A3 teaches how to pay that debt well.

Unattended means isolated

The bottom rung gets its own rule: restrict unattended modes to isolated environments — a container, a virtual machine, a sandbox. An unattended agent can run anything, and it can be misled by anything it reads, so the environment must contain whatever it does. Give it no credentials beyond the task. Assume every mistake it can make, it eventually will, with nobody there to say no. Isolation is what makes that assumption survivable.

Verified 2026-10-15

Claude Code's unattended mode is bypassPermissions, started with claude --dangerously-skip-permissions. The official docs scope it to isolated containers and VMs only — a container, VM, or the sandbox runtime, run as a non-root user. Deny rules you configure still apply in every mode, this one included. The flag name is a warning, not branding.

When the agent is the wrong tool

Some tasks are faster by hand, and handing them over is its own kind of unscoped spend. Two signs:

  • Describing costs more than doing. A one-character typo in the file you are reading, a rename your editor does in one keystroke: by the time the instruction is typed, the edit would be done. Make the edit.
  • You cannot state the check. When you cannot say what would prove the work, the agent returns confident output you can neither accept nor reject. That is not a task yet. Scope it first — or do the thinking yourself, because deciding what you want was the actual work.

Worked example: a planned task, start to finish

The task: a small CLI tool ships a cleanup command that deletes stale export files, and you want a --dry-run flag. You have never read this corner of the code. Apply the test: you cannot name the files, so you plan. The transcript is condensed; the annotations after each excerpt are the lesson. 

You (read-only planning):
The cleanup command deletes stale export files. Add a
--dry-run flag: print every file that would be deleted,
delete nothing, exit 0. Propose a plan first — name the
files you would touch, and name the test that proves
--dry-run deletes nothing.

The mode was chosen before the first token, by the naming test. And the prompt still carries A1's three parts: the goal is stated, the check is named up front, and the files — the part you could not supply — become the plan's first deliverable. 

Agent (plan, condensed):
Read cli.py, commands/cleanup.py, tests/test_cleanup.py,
scripts/nightly.sh.

1. cli.py — register --dry-run on the cleanup command.
2. commands/cleanup.py — pass dry_run into delete_stale();
   when set, print each path and skip the remove call.
3. tests/test_cleanup.py — new test: run cleanup --dry-run
   over a temp dir of stale files; assert every file still
   exists and every path was printed.

Found while reading: scripts/nightly.sh runs cleanup from
cron with no flags. The default behavior stays unchanged,
so the nightly job is unaffected.

Out of scope, noting it: delete_stale() also clears a
cache directory that the help text never mentions. Worth
a separate task.

The plan's value is its two surprises. A cron job calls this command — checked for the price of a file read instead of a broken nightly run. And the undocumented cache deletion got fenced off as a separate task instead of fixed on the fly: the plan held the scope that a mid-edit discovery would have blurred. 

You:
Good. Keep the cache-directory note out of this change.
Approve the plan — switch to approval-per-action and make
the edits.

One sentence trimmed the scope. That is the cheapest-artifact property in action: the same trim after the fact is a review argument over written code. 

[Three edits, each approved. Tests run.]
Agent: 14 passed, including test_dry_run_deletes_nothing.
Against the fixture, --dry-run prints 3 paths and removes
none.

The session ends where the prompt began: at the named check. Autonomy stayed at approval-per-action, so the verification owed stayed small — three diffs you had already approved in outline, and one test run. The verification rule, balanced.

Quiz

  1. When is it safe to skip the planning pass?

    When you can name the files and the check, the plan already exists in your head; writing it again is ritual. Request length and urgency measure nothing about scope.

  2. Which task earns auto-accepted edits?

    Mode follows the risk of the work: a scratch branch under fast tests has a blast radius you can delete. The other three have large or irreversible blast radii and earn more control, not less.

  3. A session ran for an hour with edits auto-accepted, and all tests pass. What does the verification rule say?

    More autonomy granted means more verification owed. Every prompt you turned off became review deferred to the end — the tests are one check, not the whole payment.

  4. Where may an unattended mode run?

    Unattended means nobody is there to say no, and the agent can be misled by anything it reads. The environment is the only boundary left, so the environment must contain whatever the agent does.

  5. Which task is faster by hand than through the agent?

    Describing that edit costs more than making it — by the time the instruction is typed, the fix would be done. The other three are A1's first wins: bounded, checkable, and genuinely cheaper to delegate.
