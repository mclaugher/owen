Guardrails and Add-ons

Track A · lesson 0005 · about 20 minutes

A4 ended on a line with teeth: "never read the .env file" belongs in a deny rule, because a deny rule is a fence the tool enforces in every mode. Now look at the rest of your must-nevers. If your instructions file says never declare work done while a test fails — in bold, maybe with an exclamation mark — you have written a hint and are trusting it like a lock. The file is context: the agent reads it and weighs it, like any other sentence in the window. Most of the time that is enough. "Must never happen" is not a most-of-the-time requirement. This lesson turns that bold sentence into machinery, then covers the opposite move: instructions you load less often, not more forcefully.

A rule the tool enforces

A guardrail is a rule the tool enforces automatically, with no model judgment involved. The distinction sits in who acts. An instruction is read by the agent, which weighs it against everything else in the window and almost always follows it. A guardrail is run by the tool itself: at a fixed moment, the tool executes a check you wrote, and the result — not anyone's judgment — decides what happens next. An instruction can be buried, outweighed, or forgotten at the bottom of a long session. A guardrail cannot, because nothing reads it. It just runs.

The mechanism is simple. The tool exposes fixed moments in a session — before an action runs, after a file changes, when the agent is about to declare the turn finished — and at a moment you pick, the tool runs a command you wrote. The command reports back through its exit code: the number every command hands the system when it ends, where zero means success. A passing check lets the moment proceed. A failing check blocks the moment, and your message — the command's error text — goes back to the agent, which reads the message and keeps working. The loop is mechanical at the bottom and adaptive at the top: the tool enforces, the agent responds.

When does a guardrail beat an instruction? Two tests, both must pass. First: use a guardrail for anything that must never happen. If discovering a single violation would upset you, the rule is guardrail-shaped; if the rule is a preference or a judgment call, the instructions file is the right home. Second: a guardrail needs a mechanical check — a command that can answer yes or no. "The tests pass" is such a command. "The code is readable" is not, and no settings file will make it one. The deny rule you wrote in A4 already passed both tests: it is a guardrail that fences where the agent may reach. Today's guardrail fires at a moment and checks the state of the work.

Verified 2026-10-30

In Claude Code, guardrails are hooks, per the hooks reference: commands the tool runs at named moments. PreToolUse fires before a tool call, PostToolUse after one, and Stop when the agent finishes responding — the "declaring done" moment this lesson uses. Hooks are configured under a hooks key in the same settings files as A4's permission rules: ~/.claude/settings.json, .claude/settings.json, or .claude/settings.local.json. A hook command that exits with code 2 blocks its moment, and the command's error text is handed back to the agent.

The loop, end to end

Theory done; now watch the loop run. The practice folder below holds a program, slugify.py, that turns a post title into a slug — the lowercase, hyphen-separated form of a title that goes in a web address. Next to it sits test_slugify.py with four tests, and one of the four fails, because the program has a real bug. Resist the reflex you trained in A4. The bug is not the exercise. The exercise is what you build around the bug before anyone fixes it.

Practice folder

Download the practice folder, then unzip it next to your other projects. The button works offline. Download it again for a fresh copy.

Part one of the exercise — six steps, about ten minutes:

  1. Download and unzip. The button above saves the folder 0005-guardrails-and-add-ons. Inside: README.md, slugify.py, test_slugify.py, and a CLAUDE.md — a lean one this time, the shape your A4 trim was aiming at.
  2. See the failure yourself. README.md names the test command. Run it and read the one failure: expected output on one line, actual output on the other. That failing test is your guardrail's raw material.
  3. Add the guardrail. Create the folder .claude inside the practice folder, and in it a file settings.json holding the block from the callout below. Read the block before you paste it — every key in it is a word you now know.
  4. Watch it fire. Start a session in the practice folder, in the mode that asks. Now ask something that has nothing to do with tests — "what does slugify.py do?" is perfect. The agent answers and tries to finish. At that moment the tool runs your check, the check fails, and the finish is blocked: your message comes back to the agent, and the agent — told that a test fails and the work is not done — gets back to work on the failure. Nothing about your question involved tests. That is the point: no model judgment anywhere in the trigger.
  5. Let the fix happen. The agent will propose the repair to slugify.py; review the diff like A3 taught you, approve it, or make the fix yourself by hand. Either way, re-run the test command and watch all four tests pass.
  6. Watch it clear. The agent finishes its reply again — and this time nothing blocks, because the same check now exits zero. The silence is the guardrail passing. What you built is a folder where no session can declare work done while a test fails. Notice what that sentence does not contain: any appeal to the agent's attention, memory, or good behavior.
Verified 2026-10-30

The guardrail, for .claude/settings.json in the practice folder — strict JSON, a plain-text settings format where every bracket and comma counts, per the hooks reference: 

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 -m unittest -q 2>/dev/null || { echo 'A test fails, so this work is not done. Run python3 -m unittest -v and fix the program, not the test.' >&2; exit 2; }"
          }
        ]
      }
    ]
  }
}

Stop is the moment the agent finishes responding. The command runs the tests quietly; on failure it prints one message and exits with code 2 — the code that blocks. The test runner itself reports failure with exit code 1, which would not block, so the command wraps it. The text after echo is exactly what the agent receives, so write it the way you would brief a colleague: what is wrong, and what to run. In an interactive session, Claude Code holds back a folder's hooks until you accept the trust dialog for that folder — and a hook is a command, so read it before you trust it.

Two honest boundaries before you fall in love. First, a guardrail is blunt: your check runs at every finish, even after the innocent question in step 4 — you watched that happen. The bluntness is the value and the price; put a slow test suite in a Stop check and you will feel the price. Second, a guardrail is only as good as its check. Yours enforces "the test command passes," not "the work is correct" — a session that weakened a test would slide right past it. That is why the practice folder's CLAUDE.md carries the line fix the program, never a test: context guarding the guardrail. The two layers are not rivals. Machinery holds the line; instructions explain where the line is.

Add-ons: instructions that load when needed

Now the opposite move. A4 taught you that the instructions file loads whole into every session, so every line must earn its place in all sessions. But some of your best instructions are occasional. A release checklist. A migration recipe. The style rules for one odd corner of the codebase. Paste any of those into the instructions file and you tax every session for a document most sessions never need — the primer's math again, and this time the right answer is not trimming. It is a different container.

An add-on is a folder of packaged instructions with a name and a one-line description. The description is always present — a standing line in the window, so the agent knows the add-on exists. The full instructions load only when the task calls for them, or when you invoke the add-on by name. Loading on demand beats loading everything always. The three-hundred-line release checklist costs its whole self in release sessions and one line everywhere else. That is the entire idea, and it is the primer's lesson wearing a new coat: tokens are the budget, and an add-on is a way to spend them only where they buy something.

The standing line is still a cost. Install ten add-ons and every session pays ten description lines on every turn, used or not — a quiet tax that grows one harmless install at a time. So judge add-ons the way you judge dependencies: one at a time, never a bundle wholesale. A bundle is sold by its best member and paid for by all of them. For each add-on, answer three questions. What does it load? Open its instructions file and look; the tool can measure the cost for you. When does it load? Which tasks pull the full body in, and how often are those your tasks? Does it earn its place? Would you otherwise retype these instructions often enough to pay the standing line — A4's test, applied per add-on. And one more habit from A3: an add-on is instructions your agent will follow, and some ship commands that run. Read it before you install it. You own the setup with your name on it.

Verified 2026-10-30

In Claude Code, add-ons are skills, per the skills docs: a skill is a folder holding a SKILL.md file — a name, a one-line description, and the instructions. A personal skill at ~/.claude/skills/<name>/SKILL.md loads in all your projects; a project skill at .claude/skills/<name>/SKILL.md is committed and shared with the team. The description loads on every turn; the body loads when you invoke the skill as /<name> or when the model judges it relevant. /skills lists every skill with its context cost, and /skill-doctor reports cost and usage and flags skills you never invoke. The docs recommend keeping SKILL.md under 500 lines and moving detail into supporting files that load on demand.

Verified 2026-10-30

Collections of skills ship as plugins — bundles of skills, agents, and hooks installed as one unit — from a marketplace: a catalog that lists plugins and where to fetch each one, per the plugins docs. Anthropic's official marketplace, claude-plugins-official, is added automatically the first time you start an interactive terminal session. Run /plugin to browse it — the Discover tab shows a context-cost estimate before you install — and install one with /plugin install <name>@claude-plugins-official. claude plugin disable <name> turns one off without uninstalling. An enabled plugin's skill names and descriptions sit in your window on every turn, in every session.

Exercise, part two: judge one add-on

Fifteen minutes of practice for the second half — and the deliverable is a judgment, not an install.

  1. Browse. Open the official marketplace from the callout above and read descriptions until one names a job you actually have — commit messages, code review, whatever recurs in your week. Note its context-cost estimate before you touch anything.
  2. Install that one. One. The bundle next to it is sold by its best member.
  3. Answer the three questions in writing. What does it load — list the command and check the cost. When does it load — read its description and name the tasks that would trigger it. Does it earn its place — would you retype what it carries often enough to pay its standing line?
  4. Act on your answer. Keep it, or turn it off. Removing an add-on after a fair reading is a pass, not a failure. The habit you are building is the judgment, and it is the same judgment you will apply when a teammate shares twelve at once.

Quiz

  1. "Never declare work done while a test fails." Where should that rule live?

    "Must never happen" plus a mechanical check means a guardrail. A deny rule fences where the agent may reach; this rule checks the state of the work at a moment, which is exactly what the finish-moment guardrail does.

  2. What separates a guardrail from a strongly worded instruction?

    An instruction is context the agent reads and weighs against everything else in the window. A guardrail is a command the tool itself runs at a fixed moment — no judgment, no forgetting, no burying.

  3. Your finish-moment guardrail's check fails. What happens next?

    Mechanical at the bottom, adaptive at the top: the tool blocks the finish and hands your error text to the agent, and the agent acts on it. That loop is what turned a failing test into a fixed program in the exercise.

  4. You installed ten add-ons last month and used one. What do the other nine cost?

    The body loads on demand, but the name and one-line description stand in the window on every turn so the agent knows the add-on exists. Nine unused add-ons are nine standing lines — the quiet tax that makes "judge one at a time" worth it.

  5. A teammate shares a bundle of twelve add-ons that made them faster. What now?

    A bundle is sold by its best member and paid for by all of them. The teammate's judgment measured their work, not yours — so each add-on faces the three questions against your own week, and some will pass.

Optional: add one guardrail your team's rules already imply to your own repo. Start with the sentence in your instructions file that is secretly a check command wearing bold type.
