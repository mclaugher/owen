Where Tokens Actually Go

Shared primer · lesson 0000 · about 15 minutes

This primer teaches one mechanism: the context window. Every habit this curriculum teaches follows from how that window fills and what a full window does to the model. Learn the mechanism once, and the habits stop being rules to memorize. They become predictions you can make yourself.

One window holds everything

An agentic coding tool is a language model in a loop. The model reads your request, decides on an action, runs a tool, reads the result, and repeats. Everything the model can see while it works sits in one place: the context window. Anthropic's documentation describes the window as the model's “working memory”. The window is not a search index. The window is not a database. The window is a single, finite buffer of text.

Everything in a session lands in that one buffer:

  • Your messages, and every reply the agent writes.
  • Every file the agent reads — the whole portion read, not a summary.
  • Every command output: test runs, build logs, stack traces, diffs.
  • The agent's standing instructions and tool definitions.
  • The model's own reasoning on the way to each reply.

Nothing here is controversial. The official docs list the same inventory. System prompt, messages, tool results, documents, tool definitions, and the model's output all count. The surprise is never the list. The surprise is the arithmetic.

Tokens: the unit the window is measured in

Models read text as tokens: small chunks, each a few characters of English on average (glossary). A word is often one or two tokens. A 300-line source file is a few thousand tokens. A failing test run with stack traces is often a few thousand more. A verbose build log can be tens of thousands on its own.

Now run a plausible session in your head. The agent orients itself in an unfamiliar repo: ten file reads, roughly 40,000 tokens. Two test runs with failures: 15,000. The conversation itself — requests, diffs, explanations: 15,000. That session reached 70,000 tokens before the second hour. The window fills faster than you think, and nothing in the interface makes the filling visible by default.

Verified 2026-10-15

Current frontier- and mid-tier Claude models have a 1-million-token context window; older Claude models have 200,000 tokens. On the 1-million-token models, one reply can run up to 128,000 tokens. On older Claude models a token averages about 3.5 English characters. Models from Claude 4.7 on tokenize the same text into roughly 30 percent more tokens (glossary). Window sizes and tokenizers change between releases. The mechanism in this lesson does not.

A fuller window is a weaker model

A bigger window does not mean the model uses the whole window equally well. The official documentation states the limit plainly: “As token count grows, accuracy and recall degrade, a phenomenon known as context rot.” Anthropic's engineering guidance says the same thing from the inside: models have a finite “attention budget”. Every token added draws that budget down. The same piece says to treat context “as a finite resource with diminishing marginal returns.”

Degradation is a gradient, not a cliff. The model does not fail at some threshold. The model gets gradually worse at recalling what it read an hour ago. The model holds your constraints less firmly. The model misses that attempt three contradicts attempt one. You experience the gradient as a session that starts sharp and turns vague. The model did not change. The window did.

Why this one fact matters most

Context degradation is the primary failure mode of agentic coding. Most sessions that go wrong go wrong this way. No error appears. The window fills with reads, failed attempts, and logs until the model can no longer work accurately inside it. Every best practice in this curriculum is downstream of this fact. Each one is a prediction the window model makes:

  • Keep tasks small. A small task has a small context footprint, so the model works in the sharp part of the gradient.
  • Plan before code. Spend cheap tokens on a plan to avoid expensive correction loops. The worked example below shows the arithmetic.
  • Start fresh sessions. A new task in an old window inherits every stale token the old task left behind.
  • Verify the output. A model working deep in a full window makes exactly the confident mistakes that are hardest to spot.

The next lessons develop each habit. Here, only the mechanism matters: tokens accumulate, accumulation degrades, so where tokens go decides how well the model works.

Worked example: invest tokens to save tokens

The task: add a rate limit to a file-upload endpoint in a mid-sized service. Two ways to spend the window. The numbers below are a worked illustration with plausible magnitudes, not a benchmark. Your files, your tests, and your tool set the real figures.

Path one: straight to code

  1. You ask for the change in one line. The agent reads six files to orient itself: 24,000 tokens.
  2. The first attempt patches the wrong middleware layer. Diff and explanation: 4,000.
  3. The test run fails. Full output with stack traces: 8,000.
  4. You redirect the agent. The agent re-reads four files and tries again: 20,000.
  5. The tests fail differently. More output, more reading, a third attempt: 24,000.
  6. The tests pass: 2,000.

Running total: about 82,000 tokens. Worse than the total is the composition. The agent wrote the passing attempt in a window still holding two failed attempts and two walls of test output.

Path two: one planning pass first

  1. You ask for a plan, not code. The agent reads five files: 20,000 tokens. The agent writes a short plan naming the layer, the config knob, and the test to extend: 2,000.
  2. You spot the wrong assumption in the plan and correct it with one sentence: 500.
  3. The agent implements the corrected plan. Diff, one test run, a pass: 14,000.

Running total: about 36,500 tokens. The difference is not model quality. The difference is where the correction happened. On path one you corrected finished code. Each correction cost file reads, a rewrite, and a test run. On path two you corrected a plan, and the correction cost one sentence. Same mistake, two prices. The agent also wrote the final code in a window that held a correct plan, not past failures.

Quiz

  1. An agent reads three files, runs the tests, and replies. What counts toward the context window?

    One window holds everything: your messages, file reads, tool output, instructions, and the model's own output.

  2. What happens to model accuracy as the context window fills?

    Degradation is a gradient, not a cliff: recall and accuracy decline as token count grows. The docs call this context rot.

  3. A two-hour debugging session grows less coherent the longer it runs. What is the most likely cause?

    Two hours of reads, failed attempts, and logs fill the window. The model works in the degraded part of the gradient.

  4. In the worked example, why did the planned path cost fewer tokens overall?

    Correcting a plan costs a sentence. Correcting finished code costs re-reads, rewrites, and test runs — the debugging spiral.

  5. Which fact belongs in a dated callout rather than the lesson spine?

    Exact window sizes change between model releases, so they carry a verification date. The mechanism is durable.
