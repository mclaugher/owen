Small Sessions

Track A · lesson 0006 · about 20 minutes

A5 left you with machinery: a guardrail in a settings file, a lean instructions file, a judged add-on. Now the question that machinery answers: if you close the session right now, what do you lose? The reflex says "everything — it already knows the project." Count what it actually knows. The instructions file: on disk. The settings and the guardrail: on disk. The code, the fixes, the tests: on disk, in commits. What dies with the session is the conversation — and by the time you feel loyal to a long session, the conversation is mostly weight. This lesson teaches you to end sessions on purpose. Three habits: one task per session, the plan in a file, commits as save points.

One task, one session

The primer gave you the budget: everything in the window is paid for on every turn, and the window degrades as it fills — the agent weighs more and attends less. Now watch what a long session does to that budget. You finish task A: the diffs it read, the wrong turn it took, the test output it studied — all of it still sits in the window. Start task B in the same session and every turn of B re-pays for the full transcript of A. None of A helps B. All of A taxes B.

"But it already knows the project." Split that knowledge in two. The part worth keeping — how to run the tests, what the rules are, what the code does — lives in the instructions file, the settings, and the code itself. A fresh session reads those at the start, every time, for a fraction of what a stale transcript costs. The other part — the conversational residue of finished work — is the part a fresh start sheds, and it is the part you were paying for. So the habit: when the task ends, end the session. A new session arrives knowing everything durable and carrying nothing stale. Ending a session is not losing work. It is shedding weight the files never carried.

Verified 2026-10-30

The Claude Code session commands, per the commands reference and the CLI reference. /clear starts a new conversation with empty context — your instructions file and settings still load, because they live on disk. Pass a name (/clear report-done) to label the finished conversation in the /resume picker. /resume returns to an earlier conversation when you genuinely need one back. From the terminal, claude -c continues the most recent conversation in the current directory, and claude -r "<name>" resumes one by ID or name. /compact frees context mid-task by summarizing the conversation so far — the half-measure for the rare task that truly outgrows one window.

Write the plan into a file

A2 taught you to demand a plan before code. That plan lived in the window: you read it, approved it, and the same session built it. Fine for one sitting — but the moment a task spans two sessions, a plan in the window is a plan in the part that dies. So move it: have the session write the plan into a file. A good plan file reads like a brief you would hand a colleague: the steps in order, the files each step touches, the decisions already made, and the command that proves the work done.

The plan file splits one task into two small sessions. The plan session reads a lot — the code, the request, the constraints — and writes one small file. The build session starts fresh, reads that small file, and spends its whole window on the work. Each session stays light, and the handoff between them is exact, because nothing travels by memory. The same file pays off in every direction: tomorrow-you picks it up, a teammate picks it up, a different tool picks it up. Durable state beats a long conversation every time someone new has to arrive.

Commits are save points

You use git every day; agent work gives commits one more job. A commit is a save point: a state you know is good, cheap to return to. Commit before you let a session change anything, and reviewing the session's work becomes one git diff — and retreating from it becomes one restore, instead of an argument with the agent about undoing itself. Commit again at each working state — plan written, tests green — and a bad change costs only the distance back to the last save point, never the day.

Between sessions, the save points and the plan file are the whole handoff. The build session reads the plan, runs the check command, and sees in the history exactly how far the work got. Nothing needs re-explaining, because nothing important was ever only said.

One more way to keep a session small — named here, taught in a later course. The main session can send out a helper: a second, short-lived session that goes and reads the big thing — a sprawling codebase, a long log — in a window of its own, and hands back only a summary. The main session pays for the summary, not the reading. That is the whole idea; depth comes later.

Verified 2026-10-30

In Claude Code, the helper is a subagent, per the subagents docs: each subagent runs in its own context window and returns only its result to the main conversation. A built-in subagent named Explore handles read-only codebase search. /agents is the starting point for managing them.

The exercise: one task, two sessions

The practice folder below holds a small expense tracker, tally.py, with four passing tests in test_tally.py. Nothing is broken — a first for this course. The task is a new feature, sized so that planning it is real work: a report command, specified in README.md, with two decisions deliberately left open. You will do the task across two sessions that never meet.

Practice folder

Download the practice folder, then unzip it next to your other projects. The button works offline. Download it again for a fresh copy.

The exercise — six steps, about twelve minutes:

  1. Download and read. The button above saves the folder 0006-small-sessions. Inside: README.md, tally.py, test_tally.py, and a lean CLAUDE.md. Read README.md: the report command, its ordering rules, and the two open decisions it leaves to your plan.
  2. Make save point zero. In the folder, run git init, add everything, and commit. This one is yours by hand — you know git. From here on, every agent change is one git diff away from review and one restore away from gone.
  3. Session one: the plan. Start a session in the folder, in the mode that asks. Ask for exactly one product: "Read README.md and write a plan for the report command to PLAN.md. Change nothing else." The plan must name the steps in order, the files each step touches (tally.py, test_tally.py), the two open decisions decided, and the check command. Review the plan like A3 taught you — every step should name a file and a way to check it. Then end the session. Its entire product is one small file.
  4. Commit the plan. A plan is work. Save it like work.
  5. Session two: the build. Start a fresh session in the same folder — this one has never heard of session one. Say: "Read PLAN.md and carry it out." Watch the start closely: the new session reads CLAUDE.md, reads PLAN.md, and arrives fully briefed — you retyped nothing. Review the diff, then run python3 -m unittest -v: at least two new report tests, and the run ends OK.
  6. Commit the result. Then notice what the handoff cost you: zero re-explaining. Session two knew nothing about session one, and it did not need to — everything that mattered was in files.

That is the habit at full size. On a real task the plan session might read for ten minutes and the build session might run for an hour, but the shape is identical: read a lot, write a small brief, start fresh, build from the brief, commit at every working state.

Quiz

  1. Task A is done and committed. Task B waits. The session has been flawless all morning. What now?

    Everything worth keeping — the code, the commits, the instructions file — is on disk and greets the next session. The finished task's transcript helps task B not at all and taxes its every turn, so a flawless morning is exactly the right time to stop.

  2. You end a session and start a new one. What actually carries over?

    The window dies with the session; the disk does not. The new session re-reads the durable state — instructions file, settings, code, history — at the start. That split is the whole lesson: durable knowledge lives in files, and only the conversation is disposable.

  3. A2 taught you to demand a plan before code. Why move that plan from the window into a file?

    A plan in the window is a plan in the part that dies. A file is durable state: the build session, tomorrow-you, or a teammate reads the same exact brief. Reading the file still costs tokens — it is just a far smaller spend than dragging a whole transcript along.

  4. Where do commits fit into a session's work?

    A commit is a save point: a known-good state that makes review one diff and retreat one restore. Commit before the agent touches anything and again at each working state — then the worst change ever costs the distance to the last save point, not the day.

  5. Why does sending a helper to read a sprawling codebase keep the main session small?

    The helper runs in a window of its own. Everything it reads is paid for there and discarded with it; the main session pays only for the summary that comes back. Same budget logic as the whole lesson — keep the expensive reading out of the window you are working in.
