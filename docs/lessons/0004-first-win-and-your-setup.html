Your first win

No teaching yet. The practice folder below holds a tiny Python program, wordstats.py, that reads a text file and prints its five most common words. It has one bug, and the bug crashes the program with a clear error. This is the shape A1 called a first win: bounded scope, checkable outcome, small context footprint. It is deliberately beneath your ability — the point is to watch the loop run end to end, not to be impressed.

Five steps, about ten minutes:

  1. Download and unzip. The button above saves the folder 0004-first-win-and-your-setup. Inside: README.md, wordstats.py, sample.txt, and a CLAUDE.md you will meet later in this lesson.
  2. Reproduce the crash. README.md gives the run command. Run it and read the error — the message names the file, the line, and the failing operation.

The file every session reads first

Now the lesson. The primer established that every session starts with an empty window and forgets everything when it ends. Your scoping rules, your run commands, your "never touch that directory" — none of it survives into the next session unless something carries it. The carrier is a plain text file at the root of your project that the agent reads at the start of every session, before you type a word. Write an instruction there once and every future session opens already knowing it.

What belongs in the file is defined by the tax it removes: the rules and checks you would otherwise retype. The run command. The command that proves work is done. The rule the code cannot show, like "standard library only, by decision, not by accident." The convention a new contributor would have to be told. If you have ever corrected the agent twice for the same thing, that correction is a line in this file.

What does not belong is defined by the primer. The file loads into the context window of every session, so every line is a cost you pay again on every start — a 400-line file taxes a two-minute session as heavily as a two-hour one. And the file is context, not a contract: the agent weighs it the way it weighs any instruction, and a bloated file buries the five lines that matter under ninety that do not. Three kinds of bloat to refuse:

  • Restated defaults. "Write clean, readable code" changes nothing. The agent was not planning to write dirty code, and the sentence spends tokens to say so.
  • What the code already shows. The agent reads your files. A paragraph explaining that wordstats.py contains the code is paid for twice and needed zero times.
  • Rules nobody enforces anymore. Dead rules rot trust in the live ones. If a line no longer binds, delete it.

One more boundary, and it matters: an instruction in this file is something the agent reads, not something the tool enforces. "Never delete the data directory" written in prose is a strong hint, not a lock. For rules that must never break, the tool has enforcement machinery — that is the next lesson. The settings below are your first taste of it.

Permission settings: three worked setups

The instructions file carries what you would otherwise retype. A settings file carries what you would otherwise re-click. In A2 you chose a rung on the mode ladder per session; a settings file makes the standing parts of that choice durable: actions on an allow list run without a prompt, actions on a deny list never run at all, and everything else asks. A prompt you answer the same way every time is configuration waiting to be written down — the same release as the retyped checklist, applied to clicks.

One property does the heavy lifting: a deny rule binds in every mode. An allow list is convenience. A deny list is a fence that holds even when the session runs with no prompts at all. That is what makes the third setup below survivable. Here are three setups to read and adapt — the mode-ladder logic from A2, written down.

Cautious

Everything asks; secrets are fenced off outright. No standing approvals, so verification is spread through the session, one small yes at a time. This is the setup for a codebase you do not know yet, for risky ground like billing or deploy code, and for your first week with the tool. Its cost is interruptions. Pay it gladly where the blast radius is large.

Verified 2026-10-30

In Claude Code, settings are strict JSON under a permissions key, per the permissions docs. A cautious file:

{
  "permissions": {
    "defaultMode": "default",
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  }
}

default is the ask-before-most-actions mode from A2's ladder. Read(...) deny rules block the agent's file tools from those paths.

Balanced

The commands you would always approve — run the program, run the tests, read the git history — stop asking. Edits and everything else still ask, and the secrets fence stays. This is the daily-work setup: the prompts that remain are the ones that carry information, because every reflex "yes" has been written down. Build it from your own history — after a few sessions you know exactly which three prompts you always approve.

Verified 2026-10-30

A balanced file, for the practice folder:

{
  "permissions": {
    "defaultMode": "default",
    "allow": [
      "Bash(python3 wordstats.py *)",
      "Bash(git diff *)",
      "Bash(git log *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}

A trailing * matches any arguments, and Bash(git log *) also matches bare git log. Put the * after the subcommand: Bash(git *) would allow every git command. When you answer a prompt with "Yes, and don't ask again", Claude Code writes exactly this kind of allow rule to .claude/settings.local.json for you — the balanced setup partly builds itself.

Hands-off, with guardrails

Edits apply without asking and the routine commands run free, so the session flows — and the deny list becomes the only fence, so it gets serious: secrets, pushing, deleting. A2's two rules both apply with full force. More autonomy granted means more verification owed, so the diff review at the end is larger and non-negotiable. And fully unattended operation — no prompts of any kind — remains restricted to an isolated workspace: a container, a virtual machine, a sandbox. The deny list holds in every mode, but a fence is a complement to isolation, not a substitute for it.

Verified 2026-10-30

A hands-off file with guardrails:

{
  "permissions": {
    "defaultMode": "acceptEdits",
    "allow": [
      "Bash(python3 *)",
      "Bash(git add *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Bash(git push *)",
      "Bash(rm *)"
    ]
  }
}

acceptEdits applies file edits without asking. Fully unattended operation is a different mode, bypassPermissions (started with claude --dangerously-skip-permissions), which the docs scope to isolated containers and VMs — deny rules still apply even there. Note one limit: a deny rule stops the agent's own tools, not a script the agent runs that opens files itself; OS-level enforcement is the sandbox's job.

Verified 2026-10-30

Where these files live, per the settings docs: ~/.claude/settings.json is yours in every project; .claude/settings.json is committed and shared with the team; .claude/settings.local.json is yours in one project, and Claude Code keeps it out of git. Matching list keys merge across files. Run /status in a session to see which files loaded. One catch: defaultMode values auto and bypassPermissions take effect from user settings, not from project or local files.

Exercise: make it yours

Back to the practice folder. Both halves of this lesson are sitting in it, waiting.

Part one: trim the bloated file. Open the practice folder's CLAUDE.md. It is about a hundred lines, and it is a fair portrait of how these files grow in the wild. Trim it with one test per line: would I otherwise retype this at the start of a session? Restated defaults fail the test. Descriptions of what wordstats.py contains fail — the agent reads the file. The Friday rule fails on its own terms. What survives is roughly the run command, the expected-output check, and the standard-library rule: a file that fits on one screen. Trim by hand, or ask the agent to propose cuts and judge each one yourself. If you do ask the agent, savor the irony: the session proposing the cuts is itself obeying the bloated file, including the line that tells it to explain every change in great detail. Bloat demonstrates its own cost.

Part two: write your settings. Pick the setup that matches the practice folder's actual risk — a throwaway project with fast feedback — and adapt it. Create the settings file inside the practice folder, start a fresh session, and ask the agent to run the program: with a matching allow rule, the prompt you answered in your first win does not appear. Then write one sentence, to yourself, naming why this setup fits this work. That sentence is the A2 habit — mode matched to risk, not to patience — and it is the sentence you will reuse on your real repo, where the answer is probably more cautious than the one you just gave.

Quiz

  1. Which line earns its place in a project's instructions file?

    The test is "would I otherwise retype it?" Restated defaults, descriptions of what the code shows, and filler all cost tokens in every session and change no behavior.

  2. Your instructions file has grown to 400 lines. What is the cost?

    The file loads into every session's context window, so every line is paid on every start — the primer's math. And a bloated file buries the lines that matter, so the agent follows them less reliably.

  3. You are about to change billing code in a repo you have never read. Which setup fits?

    Match the setup to the risk of the work, not to your patience. Unknown code and a large blast radius earn maximum control; speed preferences measure nothing about risk.

  4. What does the hands-off setup require before you run it?

    The deny list is the fence that binds in every mode, and fully unattended operation stays restricted to isolated environments — A2's rule, now written into configuration. The other options are good practices, not the requirement.

  5. "Never read the .env file." Where should that rule live?

    An instructions file is context the agent reads and weighs; a deny rule is a fence the tool enforces, prompts or no prompts. "Must never happen" belongs with enforcement — the next lesson builds on exactly this line.
